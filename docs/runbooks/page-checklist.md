# Page Completion Rule

Adopted verbatim from the customer brief (architecture plan §23.3). A page is **complete** only when
every item below is true. Pages that do not meet this are labelled _temporary wireframe_ in the UI
(non-production badge) and in the progress log.

| #   | Item                             | Evidence expected                                                                    |
| --- | -------------------------------- | ------------------------------------------------------------------------------------ |
| 1   | UI implemented                   | Screenshot or review                                                                 |
| 2   | Responsive design implemented    | Mobile and desktop screenshots; Playwright `mobile` project                          |
| 3   | Navigation works                 | Reachable from the sidebar/menu; deep link works; back navigation sane               |
| 4   | APIs connected                   | No mocked data left; every call goes through the typed client                        |
| 5   | Database operations work         | Rows created/updated as expected; migrations applied                                 |
| 6   | Validation works                 | Client and server messages for invalid input                                         |
| 7   | Permissions work                 | Allowed roles see it; others get 403 or no menu entry; API test in the module's spec |
| 8   | Loading states exist             | Skeleton or spinner while fetching                                                   |
| 9   | Empty states exist               | Helpful text and the primary action when there is nothing yet                        |
| 10  | Error states exist               | Recoverable error with retry and reference id                                        |
| 11  | Success states exist             | Toast or inline confirmation after saving                                            |
| 12  | Forms work                       | Submit, discard, dirty tracking, field errors                                        |
| 13  | Tables and filters work          | Sorting, filtering, paging where present                                             |
| 14  | Related pages connected          | Links to detail/parent pages                                                         |
| 15  | Complete user journey works      | The journey (J-xx) passes end to end                                                 |
| 16  | Relevant tests pass              | Unit/API/E2E referenced in the module README                                         |
| 17  | Included in the demo walkthrough | Step listed in the demo script                                                       |

## Where the eighty pages stand

Every page of the plan's §14 inventory exists and is reachable. Five of them are not a route of
their own, because the thing they describe lives inside a page that already existed:

| Plan page                                                | Where it is                      | Why                                                                                                                            |
| -------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| DP-P07 Not found `/404`                                  | `apps/web/src/app/not-found.tsx` | Next.js renders it for any unmatched address; a literal `/404` route would be reachable on purpose, which is not what a 404 is |
| DP-P08 Error `/500`                                      | `apps/web/src/app/error.tsx`     | The same reasoning: an error boundary is shown when something fails, not navigated to                                          |
| DP-A13 Course builder `/admin/courses/{id}/edit`         | A tab of `/admin/courses/[id]`   | The builder, the settings and the publishing are one workspace; a separate address would split a single job across two pages   |
| DP-A14 Publish course `/admin/courses/{id}/publish`      | A tab of the same workspace      | As above                                                                                                                       |
| DP-A23 / DP-T09 Test grading `/admin/tests/{id}/grading` | A tab of the test workspace      | Grading is read beside the results it changes                                                                                  |

The six management metrics whose module is deliberately out of the demo (projects, trainer
performance, placement, company-wise placements, certificates, feedback) appear on the admin
dashboard and in the report catalogue as named placeholders with the reason, per plan §12.3.

## The states audit (Phase 6)

Items 8 to 11 of the rule above (loading, empty, error and success) were audited across the whole
web application rather than page by page. They are carried by shared pieces
(`apps/web/src/components/page-states.tsx`, the `sonner` toaster, `app/error.tsx`) rather than
written out again on every page, so counting the pages that use them is the honest measure.

| State   | Rule | What the code does                                                                                                                                                                                                                                                                                                                  | Gaps |
| ------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| Loading | 8    | Every one of the 68 components that fetch has a loading branch. `LoadingRows` draws a skeleton in the shape of the list or form it stands in for, and three route-level `Suspense` boundaries cover the pages whose data is fetched on the server.                                                                                  | none |
| Empty   | 9    | `EmptyState` (text plus the primary action, per plan §979) in 37 components. Every other `.map` is either guarded by a length check or walks something that cannot be empty: a constant status list, a tab strip, or a `<select>` whose first option is already "Not set".                                                          | none |
| Error   | 10   | Every one of the 68 fetching components has an error branch. `ErrorState` gives the message, the request id as a reference, and a "Try again" button (plan §981, inline retry). All 46 forms report a failed submit inline or as a toast. `app/error.tsx` is the full-page boundary and prints the Next.js digest as the reference. | none |
| Success | 11   | All 46 components that mutate confirm it: a toast, a redirect to the thing just made, or inline text.                                                                                                                                                                                                                               | none |

The audit found one defect, now fixed. The practice code editor sent "Run my own input" through the
grading path with an expected output that could never match (a literal NUL byte in the source), so
a learner asking what their code prints was answered "Did not pass". Running one input is now its
own function, `runOnce`, with its own panel and no verdict, because nothing is being judged.
